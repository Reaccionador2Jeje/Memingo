# Memingo Android Native — Architecture

Status: A0 and the A1 native project generator/build driver are implemented on feat/android-native-foundation. APK production still requires a local JDK, Android SDK and Gradle installation.

## Goals

Memingo will be able to create real Android applications from Memingo projects. The generated application must be a native Android application, not a WebView wrapper. The first backend will generate Kotlin source and an Android Gradle project, then use the official Android build toolchain to produce APK and AAB artifacts.

Memingo Studio is developed in parallel. The existing IDE repository is the home of the user-facing workbench; the Memingo language repository remains the source of truth for the language, CLI, project model, Android generator and build integration.

## Important existing architecture

The current Memingo runtime is a Python package (Python >= 3.10), with a lexer, parser, AST/interpreter, standard library, CLI, package manager and LSP. Do not replace this foundation with a new Rust compiler as part of this initiative. A future native compiler can be evaluated independently, but it is not a prerequisite for Android support.

The existing `memingo build` command creates project archives. Keep that behaviour stable. Android builds must use explicit platform commands rather than silently changing the meaning of `memingo build`.

Memingo IDE is a separate repository. It already contains:
- An Electron desktop workbench.
- A Capacitor-based Android editor package.
- Android debug/release packaging for the IDE itself.
- A browser/mobile editor with local editing and lightweight language intelligence.

Those features package the IDE. They do not yet generate arbitrary native Android applications from Memingo projects. Reuse the IDE workbench and its existing Android build pipeline where appropriate; do not confuse the IDE APK with an app generated by Memingo.

## Target developer workflow

Current A0 CLI surface:

```bash
memingo android init MyApplication --application-id com.example.my_app
memingo android check MyApplication
memingo android generate MyApplication
memingo android build MyApplication

# Planned for later milestones:
memingo android build --release
memingo android run
memingo android doctor
```

The A1 generator creates a predictable project layout (Gradle scripts are pinned; the wrapper is created with the installed Gradle distribution when desired):

```text
MyApplication/
├── memingo.toml
├── main.mgo
├── android/
│   ├── settings.gradle.kts
│   ├── build.gradle.kts
│   ├── gradle.properties
│   └── app/
│       ├── build.gradle.kts
│       └── src/main/
│           ├── AndroidManifest.xml
│           ├── java/<package-path>/MainActivity.kt
│           └── res/
└── assets/
```

Generated files should be clearly marked as generated. User-owned assets and configuration must not be overwritten during regeneration.

## Architecture

### 1. Project model

Extend the existing Memingo project manifest with a versioned, optional Android configuration. Keep generic project metadata separate from platform-specific settings. Validate application ID, version, minimum SDK, target SDK, permissions and asset paths before generation.

### 2. Language frontend

Reuse the official Memingo lexer, parser and AST. Add app/UI language constructs only through deliberate, tested grammar changes. Do not invent a second parser inside Studio. The initial app model should be explicit and versioned so future syntax changes can be migrated.

### 3. Android intermediate representation

Introduce a small platform-neutral application model for:
- Application metadata.
- Screens and navigation.
- Native UI components and layout.
- User events and state.
- Resources and assets.
- Requested Android capabilities.

Validate the model before code generation. Keep this application IR separate from the interpreter's existing expression AST.

### 4. Kotlin/Android backend

Generate Kotlin source using native Android APIs. Jetpack Compose is the proposed UI toolkit for the first release. Generate the manifest, resources and Gradle project from pinned templates. Keep generated Kotlin readable and deterministic so developers can inspect and extend it.

The first release should support a deliberately small component set (text, button, text input, column, row, spacing and navigation) before adding advanced device APIs.

### 5. Build driver

The build driver should:
1. Check the project and Android configuration.
2. Verify the required JDK, Android SDK and Gradle toolchain.
3. Generate or refresh only Memingo-owned files.
4. Invoke Gradle with argument arrays (never shell-string interpolation).
5. capture diagnostics and map generated Kotlin/Gradle errors back to source locations where possible.
6. Report the exact APK/AAB output path.

Pin Android Gradle Plugin, Kotlin and Gradle wrapper versions. Do not download or execute arbitrary build scripts supplied by dependencies. Release signing must use user-provided local credentials or CI secrets; never store signing passwords in project files or logs.

### 6. Runtime and platform APIs

The first release should compile application logic into Kotlin. It must not embed a Python interpreter in the APK. Expose platform features through a documented Memingo Android SDK with typed wrappers and explicit permission declarations. Add capabilities incrementally and explain runtime permission requirements.

### 7. Studio integration

Extend the existing Memingo IDE repository rather than creating a second IDE. Studio should:
- Recognize Android-enabled Memingo projects.
- Offer Android project creation.
- Provide project diagnostics and generated-source inspection.
- Run check/build tasks through a narrow, allowlisted bridge to the Memingo CLI.
- Display Gradle output and artifact locations.
- Offer device/emulator deployment only when the required Android tooling is available.

The Capacitor mobile editor can edit projects, but native app compilation on Android devices is a separate capability and is not required for the first Studio milestone. Desktop/Linux build support comes first; remote build execution can be considered later.

## Milestones

### A0 — Foundation
- [x] Add Android project configuration under a versioned [android] manifest section.
- [x] Add Android project validation and CLI diagnostics.
- [x] Add memingo android init and memingo android check without changing existing commands.
- [x] Add tests for manifest preservation, application ID validation, SDK ranges and entry-point checks.
- [ ] Add generator/template ownership rules (required when A1 creates generated files).

A0 configuration example:

```toml
[android]
schema_version = 1
application_id = "com.example.my_app"
min_sdk = 23
target_sdk = 35
version_code = 1
version_name = "0.2.0"
ui = "compose"
```

The first command adds this section to an existing Memingo project without replacing its existing manifest or source files. It refuses to overwrite an existing [android] section. The checker validates the application ID, SDK ranges, version metadata, supported UI toolkit and Memingo entry file. A0 only adds metadata. A1 adds deterministic Kotlin/Compose and Gradle project generation. `memingo android build` invokes the installed Gradle toolchain; it does not download SDKs or wrapper binaries automatically. An APK is reported only after Gradle succeeds and the expected artifact exists.

## Compatibility and non-goals

- Preserve the current Memingo syntax and interpreter behaviour.
- Preserve `memingo build` archive behaviour.
- Keep Python 3.10+ as the current runtime requirement.
- Do not require Rust for the Android backend.
- Do not make Android Studio itself a prerequisite for generated projects; use the command-line Android SDK/Gradle toolchain.
- Do not promise iOS, desktop-native or game-engine output until those backends have separate tested designs.
- Do not claim a generated APK is ready until an actual build and install smoke test passes.

## Definition of done for the first milestone

A user can create a fresh Android project, open it in Memingo Studio, run validation, generate native Kotlin/Compose sources, build a debug APK, and install/launch that APK on an Android device or emulator. Existing Memingo tests and CLI commands continue to pass.
